# Contributing

## Clean-room rules

This is a clean-room implementation. Read [CLAUDE.md](CLAUDE.md) and the
[clean-room protocol](.claude/skills/provision-workflow/references/clean-room-protocol.md)
before contributing. In short:

- Implement only what `specs/` and open standards say. Product-derived
  material enters the repository only as audited functional specs.
- Never use vendor source, binaries, decompiled output, packet captures,
  license-gated content, or confidential material. No reverse engineering.
- No vendor product names in code, crate names, config keys, paths,
  comments, or log text. `scripts/check-names.sh` enforces this.

### Test data and fuzz corpora

Test fixtures (anything under a crate's `tests/` or loaded by a test) and
fuzz corpus seeds (`fuzz/corpus/<target>/`) must be one of:

- generated by our own code or tests, or
- hand-built from an open-standard description (RFC, UEFI, PXE, or the
  publicly documented Microsoft format), or
- a published open-standard test vector (for example, an RFC appendix).

Never use packet captures, logs, disk or boot images, or any other file
taken from a deployment of the vendor product, not even a lab one.

Record the origin of every fixture and seed in a `SOURCE.md` next to it
(`fuzz/corpus/<target>/SOURCE.md`, or the fixture's directory). Give each
file name its origin: the generator and its arguments, or the standard and
section it was built from. A fixture or seed with no recorded origin is
rejected in review.

## Build prerequisites

- Rust from `rust-toolchain.toml` (rustup installs it automatically).
- For the FIPS module (decision 0001): a C compiler, CMake 3.x or later, Go,
  and clang/libclang.
- Supply-chain tools: `cargo-deny`, `cargo-audit`.
- Fuzzing: `cargo-fuzz` and the nightly pinned in `fuzz/rust-toolchain.toml`.

Build the FIPS module from the bundled crate source only.
`.cargo/config.toml` sets `AWS_LC_FIPS_SYS_USE_SYSTEM=0`,
`AWS_LC_SYS_USE_SYSTEM=0`, and `AWS_LC_FIPS_SYS_STATIC=1` for every Cargo
build in this repository, as CI does. Without them, the AWS-LC build scripts
probe `OPENSSL_DIR` and pkg-config for a system library and may adopt one.
Do not override them in your environment.

FIPS results on macOS are **functional only**: macOS can compile and
self-test the module but is not evidence of a validated operational
environment. The authoritative FIPS build is Linux CI.

## Gates

Run `scripts/gates.sh` before asking for review. It runs, in order: format
check, clippy with `-D warnings`, tests, doc tests, a binary build, the
FIPS-linkage check, the pure-Rust check, the name check, `cargo deny check`,
`cargo audit`, and markdownlint. It records every command's status and
continues past failures.

## Pure-Rust rule

No C/C++ toolchain dependencies: no `-sys` crates, `cc`/`bindgen` build
scripts, or vendored C (`scripts/check-pure-rust.sh`, `deny.toml`). The
only exceptions are written decisions:

- [0001](docs/decisions/0001-fips-validated-crypto.md) (with Amendment 1):
  the FIPS-validated AWS-LC module and its build-only tools, confined to
  `usgp-crypto`.
- [0002](docs/decisions/0002-fuzz-harness-native-code.md): libFuzzer in the
  separate, unshipped `fuzz/` workspace.

`unsafe` is forbidden workspace-wide. A crate that truly needs it requires a
decision record, and every block carries a `// SAFETY:` comment.

## Compliance annotations

Code that implements a control or requirement carries a mapping comment:

```rust
// COMPLIANCE MAPPING:
// - NIST 800-53: SI-10 (Information Input Validation)
// - SPEC: specs/boot-network.md#REQ-BOOT-004
// - RFC 2347 §2 - option negotiation
```

Known gaps get a `// POAM: <description>` comment and an entry in
`docs/compliance/POAM.md`. Every change updates `docs/compliance/`; claims
must be backed by code and passing tests.

## Commits and changelog

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
`<type>(<scope>): <summary>`, where the scope is a crate name without the
`usgp-` prefix, or `ci`, `deps`, or `docs`. The types are `feat`, `fix`,
`perf`, `refactor`, `test`, `docs`, `build`, `ci`, and `chore`. Mark
breaking changes with `!` or a `BREAKING CHANGE:` footer.

Every user-visible change adds an entry under `## [Unreleased]` in
[CHANGELOG.md](CHANGELOG.md). Entries are grouped by crate, and security
fixes go under `### Security`.

## Versioning

All workspace crates share one version (`[workspace.package] version`).
Before 1.0.0:

- a breaking change or a new feature bumps the minor version
  (0.1.0 to 0.2.0);
- a backwards-compatible fix bumps the patch version (0.1.0 to 0.1.1).

`0.0.0` means unreleased. The first tagged release is `0.1.0`. Only the
release engineer changes the version, and only when the owner asks for a
release.

## Agents

Agents working in this repository never commit, push, or switch branches
unless the user asks.
