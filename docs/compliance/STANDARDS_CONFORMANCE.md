# Standards conformance

Open standards implemented, by section, with any deviation. Section
references use the repo summaries in `specs/standards/` (`pxe-dhcp.md`,
`proxy-dhcp.md`, `dhcp-long-options.md`, `tftp.md`, `uefi-guid-text.md`,
`uefi-secure-boot.md`; for M2 also `http-tls.md`, `security-baseline.md`,
`wim.md`, `wim-compression.md`). WIM facts the summaries do not state are
cited to our own DISM observations `OBS-nnn` in
[`docs/formats/wim-observed.md`](../formats/wim-observed.md) (decision
0006; sample runs R1 and R2).

Status values:

- **Implemented (in-process)**: code exists and in-process tests pass.
- **Live**, added after the status: the section was also exercised in boot
  smoke run CI 40438138720 (2026-10-27, Linux, KVM), either by OVMF
  firmware (edk2 build, digests in `docs/compliance/ATO_EVIDENCE.md`) or
  by the S4 lab probe, as named. One firmware build in one lab topology;
  it is not a claim about other firmware.
- **Not implemented**: the relay never uses or acknowledges it.
- **Implemented (in-process, M2)**: M2 code exists and its tests passed
  in the M2 QA run or, where marked "fix-round", in reviewers' local
  re-runs after it, on the macOS development host (functional evidence
  only). "DISM R1 (local)" means the DISM-made samples of run R1 were
  checked on macOS.
- **WIM CI**, added after an M2 status: the Linux `verify` job of
  `wim-samples` runs 40601244164 and 40601244679 (commit d72b761,
  2026-10-27) passed against DISM samples S01 to S07, S09, S10, S11A,
  S11B, S12A and S12B with the committed checker. "Fuzz CI" means
  600 s `fuzz-smoke` in CI run 40601242085 (same commit), built without
  ASan (POAM-37).
- **S11/S12 local**: the uncommitted S11/S12 change (2026-10-27) passed
  only the coder's and reviewers' runs on macOS against copies of R1 and
  R2. It has no QA run and no CI run.

"Project design" in the Deviation column marks a rule the standards do not
state. It is our choice (OPEN-BOOT-L1 for numbers), not a claim about how
any product behaves.

| RFC 2131 | §4.1, requests on port 67 from outside the interface subnet | Implemented (in-process) | **Project design (SC-5)**, no standard states it. A request on port 67 with `giaddr` 0 from a source outside the receiving interface's subnet is dropped (`off_segment_source`) when `ciaddr` is not that source. When `ciaddr` equals the source and the source is a unicast host, it is answered by unicast to `ciaddr`:68 (step 2), charged to the routed budget, so no broadcast is possible. The follow-up port to a proxy that answered on 67 is unconfirmed (`proxy-dhcp.md` §9), so routed clients with an address are answered on both 67 and 4011. Observed in CI 40438138720 (one firmware build, not a standard statement): in all six OVMF network boots (S1, S2, S5, S6 lifted, S8 both guests) the firmware sent its follow-up request unicast to the relay's UDP 4011 from its own port 4011, including the two routed guests, which sent it directly to 10.20.1.2:4011 rather than through the relay agent. The relay logged no ACK on port 67 to any OVMF guest. The port 67 path for routed clients was not exercised by firmware. |

| RFC 1542 | §4.1.1 hops limit | Implemented (in-process) | Project design: the relay, acting as the server, drops requests with `hops` above 16, the relay-agent limit. |

| RFC 3396 | Long and repeated options (`dhcp-long-options.md` §2, §3, §4, §6, §7) | Implemented (in-process); live by S4 probe: repeated and split option vectors answered or dropped by their joined value (CI 40438138720) | Only the 11 options the relay reads are joined.
